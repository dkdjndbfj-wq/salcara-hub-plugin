# 服务器端透明中继、节点池与后台改版设计

日期：2026-11-06；实现状态更新：2026-11-07。

本文件记录总体设计与分阶段交付状态。当前已实现固定回源 Edge、HTTP / SOCKS5 节点池、多节点负载均衡、容量与有界队列、真实运行计数，以及通过 SSH 接入主机并部署 Linux Edge 的管理流程。后台 UI 的 66 项自动化测试已通过，真实 Edge 浏览器也完成了桌面与手机宽度的模拟 API 交互验证；这些结果不代表真实 VPS 部署或公网加速验收。当前支持范围与部署方式以 [服务端入口与线路管理](SERVER-NETWORK.zh.md) 为准。普通订阅不自动成为公网入口，复杂协议仍需要已有 Mihomo 服务，订阅暂按快照导入。

本稿替换此前的客户端选路方案。用户已明确：节点只由管理员在 Hub 侧管理，电脑和手机照常访问 Hub，不选择节点、不取得订阅或节点凭据。

## 1. 用户要求的链路是否可行

目标链路是：

```text
用户电脑 / 手机 ⇄ 可接受用户连接的节点入口 ⇄ Hub 所在 VPS
```

这条链路可以实现。节点在这里承担反向代理或中继入口的职责。域名可以仍使用原 Hub 域名，由管理员将其解析或接入到节点入口；节点将连接转发到真正的 Hub。用户不需要了解节点，也不需要安装或配置 VPN。

但“买了 VPN 节点使用权”不必然包含“将该节点配置为自己的 Hub 入口”的能力。是否能直接使用已购 VPN，取决于供应商提供的功能；目前尚未验证具体服务商。

## 2. 普通机场订阅与可用入口的区别

| 已购服务提供的能力 | 能否实现上述链路 |
| --- | --- |
| 仅有 Clash / Mihomo 兼容订阅、HTTP / SOCKS 等普通出站节点 | 单凭在 VPS 导入订阅通常不能实现。用户请求仍先到原 VPS，不会自动在抵达前经过节点 |
| 可配置公网端口转发 / 入站映射，能转发到 VPS 的 VPN 隧道地址 | 可以，需验证公网端口、双向回程、HTTPS 和长连接支持 |
| 可配置域名回源的反向代理、加速入口或中继服务 | 可以，节点接受用户连接后回源到 Hub |
| 具有节点服务器管理权 | 可以部署受控转发入口；跨节点线路质量仍需实测 |

“普通代理节点能替客户端连接 Hub”本身成立，但通常要求客户端先用代理协议、节点凭据连接它。用户已排除这种客户端代理方案，因此本项目不能依赖该条件。

不要求额外购买服务器：如果现有 VPN 已提供入口能力，就使用它；如果只提供出站能力，仅修改 Hub 软件无法创造缺失的公网入口。新增可控中继或购买相应入口服务属于另一种部署选择，不能默认为用户已经拥有。

## 3. 在 VPS 开全局代理为什么不等于实现

Hub 的现有手机和电脑连接主要采用 HTTP 与 SSE，由客户端主动发起。服务器对这些连接的回复不会通过普通 HTTP / SOCKS 出站拨号器重新发起。

若用户连接的是 VPS 的公网地址，而 VPN 把返回包的源地址改成另一个出口地址，原 TCP 连接也无法直接接受这些包。专门支持保留 VPS 公网源地址的路由隧道有可能优化返程，但需要供应商与上游明确支持，不能以普通 TUN 或 WireGuard 配置推定已具备。

本次用户确认的“用户先到节点，再由节点到 Hub”以入口中继方式设计，不混同于上述返程路由。

## 4. 入口模式成立后的项目设计

以下保留总体架构约束。当前落地的是固定 Hub 回源的 HTTP / SSE Edge 入口；四层透明转发、VPN 路由隧道和主动反向隧道是部署方案讨论，不表示本项目已实现这些能力。

1. 管理员在 Hub 后台添加供应商连接信息或可控入口，配置回源目标。
2. 保持一个对用户公开的 Hub 域名；入口需支持相应公网端口。若只有随机映射端口，不能承诺原 HTTPS 地址完全不变。
3. 优先采用保持 TLS 端到端到 Hub 的四层转发；采用 HTTPS 反向代理时，明确证书终止位置和供应商的信任范围。
4. 入口与 Hub 之间可以使用 VPN 隧道或受认证回源连接；VPS 主动建立反向隧道也是可行方式，但隧道另一端仍须有可接受用户连接的入口。
5. Hub 继续保存唯一的设备与配对状态，切换网络路径不更换站点身份、不重新配对。
6. 订阅、节点密码和控制接口仅留在服务器管理侧。

## 5. 代理池与自动切换的范围

- 当前订阅节点导入表示通过格式与协议检查；尚未测量的 `unknown` 节点允许最多一个业务请求或流连接试探，不要求先完成公网入口能力验证。是否可承载实际中继链路、是否改善用户体验，由管理员在上线前验证；按供应商入口 / 出站能力分类仍是后续目标。
- 多节点自动切换由服务端控制。优先在稳定公网入口之后切换回源线路，避免每次切节点都改变用户入口。
- 若不同节点只有各自公网入口，需要供应商统一入口、负载均衡或 DNS 切换；这些是实际部署依赖，不能由一个本地节点列表替代。
- DNS 切换受缓存影响；TCP / SSE 也不能因节点切换无损搬迁。保持健康旧连接，新连接用新路径，故障时通过现有客户端重连与回执恢复。
- 当前 `latency` 模式仅使用入口经候选线路到固定 Hub 的探测往返时间，并设连续失败判定、改善阈值和切换冷却；完整用户链路的失败率、抖动与延迟评分尚未实现。入口到 Hub 的探测结果不能替代用户端到端提速验收。
- 直连回退同样需要可用的入口切换机制；不能声称节点失效后所有用户立即自动回到原 VPS。

## 6. 后台改版

已实现七页导航：“概览、设备、服务器、线路与代理池、访问策略、操作记录、系统”。用户侧不出现节点列表或选路入口。

线路页显示目标 Hub、选路模式、节点健康与探测时间、实际请求和流连接占用、容量、排队及累计完成 / 失败 / 拒绝数量；支持订阅兼容性预览、勾选导入、权重与排空设置。“服务器”页提供 SSH 接入、环境预检、部署方案和任务日志。供应商能力判断、完整链路收益、带宽和近期成功率趋势仍需要后续数据采集与验收，不以界面存在代替测量结果。

当前订阅界面流程为：录入 HTTPS 订阅地址 → 预览协议兼容性 → 勾选后快照导入 → 探测入口到 Hub 的线路；现有代理地址也可手工添加后探测。确认供应商入口能力、验证公网入口与回源、对照直连测试，再决定是否承载用户流量，是管理员的上线验收流程。“仅服务器出站”等用途分类和供应商能力验证界面仍属后续目标，当前兼容性预览不代表远程连接已加速。

保留现有管理认证与 CSRF；重做长页导航、设备列表、窄屏布局和操作反馈。线路页可选择每 5 秒读取状态，服务器页仅在有运行中任务时查询进度；页面不可见时暂停。状态读取不触发全池探测。切换管理入口会使旧入口的编辑草稿与订阅预览失效，写操作同时校验入口身份与配置版本。

## 7. 实施与验收门槛

软件按通用 HTTP / SOCKS5 与 Clash 订阅格式设计，不依赖用户提供供应商名称或订阅密钥。实际部署时仍需确认可用入口及回源链路；普通订阅无法完成入口部署时，需要其他受控中继或相应入口服务。

能力成立后，用一条线路验证：普通客户端访问预期 Hub 域名，经入口到达同一个 VPS；HTTPS、指令 POST、持续 SSE 和断线恢复均正常。再扩展代理池与后台。

性能验收分别测量电脑 ↔ Hub、手机 ↔ Hub和完整远程指令往返，与同网络、相近时间的直连对照。中继增加一跳，只有它提供的线路优于原跨境路径才会更快，不承诺任意 VPN 节点都能提速。

当前结论：原生代理池调度与 SSH 托管 Edge 部署已完成代码实现；真实 VPS 的安装、恢复、承载量和公网收益尚未验收，用户所购买的具体 VPN 是否能承担入口也尚未确认。电脑和手机继续使用统一 Hub URL 与既有登记、配对流程；未分发节点凭据，未修改生产服务器网络。

### 8.1 订阅到受控 Mihomo 的发布流程

1. **录入与检测**：管理员填写订阅 URL，保存为受保护的凭据引用。安全抓取后只提取允许的节点字段，逐项报告原生可用、指定 Mihomo 版本可用或不支持；展示增删、协议和认证信息变更摘要，不显示密码。不直接运行订阅中的脚本、TUN、DNS、外部资源或控制监听配置。
2. **生成与校验候选版本**：根据已固定版本、校验过来源的 Mihomo 内核生成最小配置，记录内核版本、配置版本和兼容性结果。管理端口仅在私有通道开放，代理监听受访问限制；限制内存、CPU、进程权限与日志大小。只有经过该内核配置校验的协议才可进入下一步，不宣称所有 Clash 协议均支持。
3. **隔离试运行**：在独立进程及临时监听端口启动候选版本，不覆盖正在服务的内核。通过真实 HTTPS 回源、测试专用幂等回显和 SSE 检查证书、认证、超时及断线恢复；先不向候选版本发送真实用户执行命令。需要灰度时只分配受控比例的新连接，并可随时停止灰度。
4. **原子发布与回滚**：使用当前配置版本提交发布，持久化候选配置后切换新连接的活动入口引用。保留旧版本及已有健康连接直至排空；校验、启动、探测或发布失败均保留原活动版本。异常时可回切已验证版本，记录原因，不因回滚盲目重发 POST，也不承诺已有 TCP / SSE 无损迁移。

后台应明确显示“已检测、候选校验失败、试运行、已发布、已回滚”等阶段；格式解析成功不能直接变成“加速已启用”。支持的协议和选项列表随具体内核版本维护，内核升级同样经过候选校验、试运行和回滚流程。

### 8.2 订阅更新与凭据轮换

增加受保护的订阅记录、刷新周期、最近成功版本和更新差异。周期更新采用最小间隔、随机错峰、并发及大小限制；失败按退避重试，保留最后可用版本，不用空响应或解析失败覆盖当前节点池。节点删除、改名、凭据变化与协议变化分别处理，凭稳定身份更新或替换，不无限追加重复节点。

订阅 URL、代理凭据和内核控制令牌分离存储并加密保护，浏览器与审计记录仅显示凭据引用和版本。新凭据先校验再切换，旧凭据按可用的重叠窗口排空后撤销；供应商不提供重叠有效期时明确可能出现的重连。凭据已失效或已撤销的旧版本不能被当作有效回滚目标。订阅快照、内核配置和活动引用须能在进程重启后恢复一致状态。

### 8.3 明确两层选路职责

后续默认实施方案已细化为 [产品化路线 B 阶段](NETWORK-PRODUCT-ROADMAP.zh.md#b-把订阅变成持续可用的节点资源)：受管 Mihomo 优先采用固定逐节点映射，由 Edge 统一调度；以下内部策略组方案保留为外部 Mihomo 的整体线路兼容方式，不把共享监听端口显示为多个可独立调度节点。

| 层级 | 选择对象与职责 |
| --- | --- |
| Salcara Edge 原生节点池 | 选择直连、原生 HTTP(S) / SOCKS5 节点，或某个受控 Mihomo 的固定代理监听端口；判断该整条回源线路是否可用 |
| 受控 Mihomo | 在后台明确指定的策略组内选择内部 SS / Trojan 等兼容节点；由受限控制适配器读取实际选择和切换原因 |
| Hub 管理后台 | 保存策略、发布版本与凭据引用，展示两层状态，不在浏览器执行代理协议、不向客户端分发节点凭据 |

一个 Mihomo 监听端口不能伪装成多个已被 Edge 独立选中的内部节点。两层分别设置失败条件、冷却及回退范围，避免两个自动策略互相触发持续切换；内部节点变化与整条回源线路变化应分别记录。

### 8.4 统一 URL 与商业运维契约

客户端继续使用原公开 Hub 域名、HTTPS 端口和路径；管理员完成入口 DNS、证书、可信转发头及独立回源地址配置。保持 `SALCARA_HUB_PUBLIC_URL`、配对身份、Cookie 和 Origin 校验一致。入口更换不能要求客户端选择节点或取得订阅；若部署无法保留原域名或端口，须作为站点迁移处理，不能宣称对既有客户端完全无感。

后续增加只读观察、线路操作、凭据管理和发布管理等角色，服务端逐项鉴权。长期审计记录操作者、时间、版本、动作、结果、回滚和凭据引用，脱敏后持久化到独立存储，明确留存与查询规则；当前进程内近期事件不替代此能力。

入口高可用采用多个可用入口及明确的流量调度机制，单独验证 DNS 缓存、证书续期、控制服务失联和入口整机故障。各入口仍回源到同一个逻辑 Hub，明确配置主控、版本与幂等分发，不让多个实例并发写同一份本地配置卷。代理节点故障转移不能代替入口高可用，也不自动解决 Hub 本身的高可用。

### 8.5 发布验收标准

- **发布与恢复**：覆盖损坏订阅、空结果、过期凭据、不兼容协议、内核启动失败、保存失败和进程中断；验证旧版本保留、配置一致恢复、凭据不泄漏、过期编辑不覆盖新版本。
- **协议与业务**：通过原公开 URL 完成登记、扫码配对、授权、指令 POST、持续 SSE 和断线恢复；切换及回滚后不串用户、不重复执行非幂等命令、不将旧延迟样本显示为新测量。
- **容量与稳定性**：按预期同时在线设备数、并发 SSE、命令速率和消息大小制定负载目标，记录 CPU、内存、连接数、队列、错误率和恢复时间；在正常、峰值、慢消费者和持续运行条件下实测，不以容器资源配额代替承载能力。
- **真实链路收益**：在代表性地区、运营商、移动网和宽带上，分别采集电脑 ↔ Hub、手机 ↔ Hub，以及手机 → Hub → 电脑 → Hub → 手机的完整指令往返；用同网络、相近时间的直连对照比较 p50 / p95、抖动、失败率、重连次数和故障恢复时间。将模型推理耗时与网络回显分开。入口到 Hub 或 Hub 到节点的 RTT 只能诊断局部链路，不能替代客户端验收。
- **上线判定**：在试点前约定目标网络、样本周期、容量与收益门槛，只有实际记录满足门槛才扩大流量；不满足时保留直连或已验证线路。本设计不预填测速成绩，不保证任意订阅或节点都能降低延迟。

## 9. vm2api 参考与多节点并发调度

参考项目：[dofastted/vm2api](https://github.com/dofastted/vm2api)，本次核对固定在提交 `4c9a9392205332d7e8eadb7e22bccef56b19280b`。其 [代理池](https://github.com/dofastted/vm2api/blob/4c9a9392205332d7e8eadb7e22bccef56b19280b/src/lib/vm/proxy-pool.mjs) 将健康、剩余绑定容量和已有绑定用于分配；[调度准入说明](https://github.com/dofastted/vm2api/blob/4c9a9392205332d7e8eadb7e22bccef56b19280b/docs/performance/scheduler-admission.md) 强调最终准入时重查实时容量，区分排队与调度耗时；[代理池概览](https://github.com/dofastted/vm2api/blob/4c9a9392205332d7e8eadb7e22bccef56b19280b/web/src/features/proxies/proxy-overview.tsx) 展示已用与空余绑定容量。VM 绑定数量、并发请求数量和 VPN 实际带宽是不同指标，不能直接互换。

该版本 [根许可证](https://github.com/dofastted/vm2api/blob/4c9a9392205332d7e8eadb7e22bccef56b19280b/LICENSE) 规定商用需要独立书面授权。本项目只参考公开设计并自行实现，未引入其核心源码或依赖；若将来复用具体文件，应另行核对该文件适用的许可。

### 9.1 当前实现的准确边界

- 已提供 `manual / failover / latency / balance` 四种模式。前三种继续使用当前活动线路；新增的 `balance` 为不同请求分配多个可用节点，不再用单个 `active_id` 表示所有业务流量。
- 健康检测默认四路并发，可设为 1–16，与用户业务的并发容量无关。HTTP 空闲连接池大小也不是活动请求上限。2026-11-07 新增可配置周期、超时、恢复、地区偏好和公开状态页，当前完整契约见 [代理池调度、检测与用户状态页](PROXY-SCHEDULING-AND-STATUS.zh.md)。
- 已实现每节点与单 Edge 进程的请求 / 流连接容量、排队长度与等待时间限制、节点排空及真实运行计数。尚未实现用户身份公平、自适应容量、带宽限速、自动扩容或多 Edge 共享配额。
- 更换线路主要影响新连接。已有 SSE 仍占用原线路，断开的 TCP 不能搬到另一台代理上；恢复必须依靠既有客户端重连与命令回执。一次非幂等指令不能向多个节点同时发送来“抢最快结果”。

### 9.2 已实现的负载均衡与容量控制

`balance` 排除禁用、不可用、排空或对应容量已满的节点，按该类活动连接的加权占用 `(活动数 + 1) / 权重` 分配新流量。权重用于分流，容量用于限制准入；当前没有将近期成功率、抖动或带宽加入自适应评分。手动、主备与延迟优选的原有选路含义保持不变，容量限制和排空同样生效。

每次准入在同一临界区完成“选择节点 + 占用容量”，响应体关闭、EOF、失败或调用取消后只释放一次。SSE 流连接与普通请求分别计数，长轮询使用请求预算；探测流量不混入业务计数。节点删除、配置更新与请求结束之间保留占用释放所需的状态，配置持久化与订阅抓取不占用业务选路锁。

| 配置 | 默认值与范围 |
| --- | --- |
| 节点权重 `weight` | 默认 1，范围 1–100 |
| 每节点 `max_requests / max_streams` | 默认 64 / 16，各为 1–4096 |
| 进程 `max_requests / max_streams` | 默认 256 / 128，各为 1–4096 |
| 等待队列 `queue_limit` | 默认 64，范围 0–4096；0 表示不排队 |
| 最大等待 `queue_timeout_ms` | 默认 2000 毫秒，范围 1–30000 毫秒 |

等待同时受队列长度、等待时长与调用取消约束；队列满、超时或无可用线路会返回明确拒绝结果。排队时尚未选定节点，因此排队和准入拒绝只计入进程指标，不能将节点的零排队值解释为没有压力。跨多个 Edge 时仍须另行分配配额或协调容量，单进程上限不代表跨入口总上限。

传输错误及包括 SSE 在内的异常读体中断会记为故障并更新线路健康；调用方取消单独计数，不误报为代理故障。Hub 返回的 HTTP 429 / 5xx 计入业务失败，不单凭这些状态隔离所有代理。故障恢复采用受限试探与后续健康检查，排空节点不再接收新流量；已有健康连接自然结束。按用户身份公平分配、根据成功率逐步调权和更完整的故障归因仍属后续工作。业务命令的去重与回执由 Hub 负责，代理池不自动重放。

“自动并发”应理解为在明确上限内自动分配多人请求，不能保证节点越多单个用户就越快。上线第一阶段先采用可配置容量；自适应上限须在获得足够负载数据后再引入，并保留最小值、最大值、增长速率、冷却和回退。共享机场总带宽、入口带宽及 Hub 处理能力都可能成为共同瓶颈。

### 9.3 输入与 UI 契约

当前管理员可以粘贴公网 HTTPS 订阅 URL，或在“添加节点”填写 `socks5://user:password@proxy.example.com:1080`、HTTP(S) 代理 URI。订阅 URL 与节点 URI 是不同入口；当前不支持在订阅地址框直接粘贴整份 YAML、任意一串 Base64、shell 命令或多行 `host:port:user:pass`。电脑和手机填写公开 Hub URL，不填写这些代理内容。

后续添加“订阅地址 / 批量节点文本 / 配置文件”三个明确入口，解析后统一预览，不执行粘贴内容。批量导入显示总数、可用协议数、重复项、不支持原因和待应用差异；文件或文本与 URL 抓取分别受大小、行数和协议限制。

调度 UI 已显示实际活动请求 / 流连接与上限、两类排队数、累计完成 / 失败 / 拒绝数量；节点行显示占用、容量、权重、探测时间、排空和恢复试探状态。累计业务完成及失败包含流连接结束，取消另有后端计数；进程重启后运行计数重新开始。策略区已提供负载均衡及容量、队列参数，支持可选的可见页每 5 秒刷新；缺少数据时显示“未采集”，不填模拟负载。

近期成功率、带宽趋势、饱和节点汇总、调度评分解释与 Mihomo 内部节点状态尚未实现。冷却及改善门槛现已可编辑，地区规则按管理员标签进行。直连目前作为显式节点启用或禁用。切换受管服务器时，`controller_id` 与配置版本共同约束写入，旧入口的节点、策略草稿和订阅预览失效，防止相同版本号造成跨服务器误操作。

### 9.4 并发验收

当前已为调度与运行计数建立本地自动化验证；后台共 66 项 UI 测试覆盖新增调度参数、凭据清理、版本冲突、跨入口隔离和服务器部署交互。真实 Edge 浏览器在 1440×1000 与 390×844 下完成使用模拟 API 的交互验证，无相关控制台错误；这不替代真实代理、SSH 或公网容量测试。

部署验收仍应证明同时请求能按策略分散到多个节点且不超容量；慢 SSE 不阻塞短指令；请求取消、响应读取中断、节点删除和服务关闭均准确释放占用；恢复探测不会覆盖更新的失败事件。实际故障注入应覆盖全池失效、单节点故障、Hub 故障和队列满，并验证命令没有重复执行。多入口同时准入需要后续的共享配额方案。容量值由目标机器与真实负载测试确定，不预设未经验证的承载人数。

## 10. 通过 IP 与 SSH 接入自有 VPS（Edge 部署已实现）

vm2api 的 [接入 VPS 界面](https://github.com/dofastted/vm2api/blob/4c9a9392205332d7e8eadb7e22bccef56b19280b/web/src/features/cluster/join-dialog.tsx) 提供主机、端口、用户名、密码或 SSH 私钥、备注和跳板节点，探测后固定主机指纹。它属于远程主机接入，不是把 VPS 登录密码当成 SOCKS5 代理密码。本项目现已提供独立“服务器”管理页；节点池表单仍只接受代理地址，不接受 SSH 凭据。参考项目的备注、跳板和其他主机用途不因此成为本项目已实现的功能。

### 10.1 表单与部署职责

管理员填写服务器名称、公网 VPS IP / 域名、SSH 端口（默认 22）、用户名、密码或私钥与可选私钥口令。当前自动部署支持 Linux systemd、amd64 / arm64，以及 root 或可执行 `sudo -n` 的账户；不接受任意内网管理目标，不支持跳板选择、自建 SOCKS 出口或用途组合。有 SSH 访问权限仍不代表该主机已具备可用的公网 HTTPS 入口。

| 入口 | 管理员提供 | 系统负责 |
| --- | --- | --- |
| 导入订阅 | 供应商 HTTPS 订阅地址 | 安全抓取、协议检测、勾选后快照导入；尚无定时更新 |
| 添加现有代理 | HTTP(S) / SOCKS5 地址及代理认证 | 检查连通性，加入线路池 |
| 接入自有 VPS | 公网 IP / 域名、SSH 用户与密码或私钥 | 指纹核对、环境检查、加密保存主机、审阅方案后安装 Edge；不自动部署公网 TLS / DNS 或 SOCKS 出口 |

已实现“发现主机指纹 → 人工核对并固定指纹 → 认证与只读预检 → 保存服务器 → 生成并审阅方案 → 显式部署 → 查看结果 → 设为线路管理入口”。指纹发现只发送主机与端口，不发送认证凭据；预检提交时清空浏览器中的密码、私钥与口令。修改连接或认证信息使指纹确认和预检失效，指纹变化时停止认证。预检检查系统、架构、root / 免交互 sudo、systemd 与必需工具；端口及目录归属在安装阶段检查，控制认证和固定 Hub 回源在启动后验证。可用磁盘等更完整的预检清单仍待扩展。

方案展示回源 HTTPS 地址、架构、部署程序 SHA-256、将创建的服务与目录、监听端口及影响；只有“按此方案部署”才执行固定安装流程。部署文件来自已配置的对应架构程序，通过 SSH 上传并校验，不执行用户粘贴的任意 shell。已实现异步任务、超时、最多两台主机同时部署和每台主机的部署锁；服务器记录最多 16 台，近期任务最多 32 条。

运行服务使用专用账户，远端用户转发与管理监听分别绑定 `127.0.0.1:8790` 和 `127.0.0.1:8791`。主机记录、SSH 凭据和控制令牌通过独立密钥加密保存，不向浏览器回显。安装目录以控制令牌的哈希作为归属标记，拒绝接管不匹配的服务或未知资源。首次安装留下的本项目部分状态可在核对后重试；更新失败时尝试恢复已有程序、服务配置和 `edge-pool.json`，避免新版数据格式使旧程序无法恢复。

浏览器离开不会取消已受理的部署。Hub 重启会将原 `running` 任务标为 `interrupted`，要求先核对远端再生成方案；不承诺任务自动续跑或重启必然已完成回滚。部署完成后，显式设为线路入口会通过 SSH 管理通道检查控制认证与固定回源；用户业务仍走 Edge 的数据入口，SSH 管理连接与用户数据面是不同链路。

### 10.2 验收与用户链路

普通服务器接入成功只代表管理通道可用。当前自动部署只安装 Edge，不修改公网反向代理、DNS、TLS、防火墙或整机默认路由；公开入口仍需管理员接通并验证。安装后的本机控制认证与回源检查不等于手机 / 电脑经公网入口的端到端验收，不能把“SSH 登录成功”或“部署完成”显示为“加速可用”。

如果接入一台国内访问较快的入口 VPS，路径可以是“电脑 / 手机 → 该 VPS 上的 Edge → 订阅节点或自有代理 → Hub”；有多个出口时再由负载均衡策略分配新连接。仅将原来的 Hub VPS 接入管理，或新增线路质量相同的主机，不保证改善用户延迟。统一 Hub URL 由管理员完成域名入口配置，用户无需填写 IP、root、密码或选择节点。

真实 VPS 上线验收尚未完成，仍需覆盖密码 / 密钥口令错误、指纹变化、sudo 不足、端口冲突、部署文件缺失或上传失败、首次安装中断及重试、旧版本与配置回滚、管理通道失联、Hub 重启和公网业务恢复。当前“移除记录”仅删除管理记录与保存的凭据，不卸载远端服务；活动入口和部署中的主机禁止移除。远程卸载仍属后续能力，设计上应先排空，只删除本项目创建且能验证归属的资源。
