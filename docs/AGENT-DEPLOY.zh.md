# 给 Agent 的独立 Hub 部署指南

只部署 Salcara Hub，不修改桌面/手机 UI，不操作用户模型 Key，不调用真实 Agent 或付费模型做部署检查，也不把 CLI 检查说成原生桌面能力验收。Bot 是电脑与手机之间的中继，Codex、Claude CLI 和其他 Agent 仍运行在用户电脑。遵循用户授权；不得把服务器密码、管理密钥、设备秘密、原站 JWT、私钥或真实配置提交 GitHub、写入公开报告或发到聊天。

Bot 安装与续跑只能完成本地健康和未认证公开路由检查，不能宣布任务已可用。签发成功后仅交付私有 `bot-binding.json` 的路径，让用户通过可信文件渠道自行导入；不把 JSON、`invite` 或 `signature` 输出到终端、工具结果、报告或聊天。该包最多可登记 8 台电脑和 1 部手机；它虽不含管理密钥，仍是允许新增绑定的敏感邀请。

## 部署前只读检查

1. 确认 SSH 主机身份、系统/架构、内存和磁盘余量；密码仅通过不回显登录输入，不写命令参数或文件。
2. 检查本机 Docker/Compose、容器名/镜像/端口、Hub 数据卷和目标安装目录。不要全量输出容器 Env、`.env`、数据库密码或日志。
3. 确认站点的 HTTPS 反代实际在宿主机还是容器，找准该域名的 `server` 配置，保留原模型、API、根目录和 TLS 路由。
4. 有旧 Hub 数据就走 [旧版迁移](STANDALONE-DOCKER.zh.md#旧版迁移)，不能重新初始化或另造空卷；目标配置有冲突或服务器余量不足时先报告，不停止原服务腾空间。
5. 确认可长期维护的公开 HTTPS 地址及 DNS/入口归属。没有稳定域名、入口或用户通过可信渠道提供的新地址，客户端不能凭空发现服务器的新 IP。

## 首次部署

Bot 任务必须显式选 `bot`，不可沿用默认 Station 模式。取得正式 Hub 源码并审阅 `deploy/standalone/install.sh`，然后在**具备公开 HTTPS 与 Docker/Compose 的目标 Linux 主机**运行：

```sh
bash deploy/standalone/install.sh \
  --mode bot \
  --public-url https://relay.example.com/salcara-hub \
  --install-dir /opt/salcara-hub-bot
```

必须把占位域名换成用户指定并控制的实际域名。脚本的 Station / Bot 目标均固定为 `0.5.4`；执行前须独立确认对应正式 Release 和公开镜像可用，本文不是发布或上线凭证，不可回退到旧版。若正式镜像不可用，只有在用户明确选择源码部署、已审阅的 Bot 源码提交完整、工作树干净且目标主机可构建 Docker 镜像时，才显式加 `--source-build`；构建会从 Git 提交归档取源码，并在初始化前运行 Dockerfile 中的全量测试、`vet` 和竞态测试。源码构建不等同于正式发布。脚本不修改 Nginx、不安装/重启 Docker、不控制远程 Docker，也不会将初始管理密钥打印出来。

Bot 安装器只检查本地 Hub 健康、公开 HTTPS `/v1/ping`，以及使用固定虚拟设备 ID、没有设备凭据的 Bridge/App 入口请求是否返回预期的 `400` 或 `403`。这不是已认证 SSE、长轮询保活、反代无缓冲或真实任务往返测试。基础检查通过后，安装器可通过管理 API 创建并私有保存 `bot-binding.json`，但只输出文件路径。可以先配置反代再安装；也可以先运行安装器启动 Hub，再完成以下反代步骤并运行续跑命令。镜像获取和源码构建失败都发生在创建部署目录及初始化数据之前；首次初始化未确认成功时不会给出续跑命令：

- 备份准确站点配置到新建、权限受限的目录，合并两个 Hub location；禁止覆盖整个文件。
- 宿主机 Nginx 使用回环 upstream；容器 Nginx 使用专用私有网络及持久化网络别名，不使用该容器自己的 localhost，不公开 8787。
- 反代需配置长连接支持、`proxy_buffering off`、足够的读超时及 `/salcara-hub` 前缀；这些配置要求不等于已经过真实连接验证。只对实际部署的主机地址做授权范围内的公网检查。
- 保留 `access_log off`，检查 CDN/WAF 的完整 URL 日志。CDN real IP 只信任明确范围，覆盖而不是追加 `X-Forwarded-For`。
- 在准确代理内先测试配置，成功后只 reload 代理。失败就恢复此次修改，不重启 Docker、Sub2API 或整台服务器。

不要在未授权时直接改 Sub2API 数据库添加菜单。给用户 URL，让用户从自定义 iframe 设置中添加。

### Bot 失败续跑

安装器若在初始化后遇到公网反代暂不可用，会保留安装目录和数据卷，并打印只续跑命令。先修复反代，再在同一台 Linux 主机运行：

```sh
bash /opt/salcara-hub-bot/resume-bot.sh --install-dir /opt/salcara-hub-bot
```

该命令只验证并启动原 Bot 容器，不运行 `-init`、不新建/删除卷、不停止其他服务；检查范围与首次安装相同。源码构建模式会优先检查本地镜像 ID，必要时从权限受限的镜像归档恢复；不会悄悄改拉 Registry 镜像。若平台没有公开 HTTPS 入站服务，基础检查不能完成；即使基础检查通过，真实 SSE/长轮询仍可能受代理限制。不要安装未授权的 VPN/隧道，也不要声称已经完成设备或任务验收。

已有同 URL 的绑定文件只有在权限、文件类型和本地结构检查通过后才会复用，并且只输出路径；**复用不是签名验证，也不证明邀请仍有效、未撤销或有剩余名额**。没有绑定文件且没有待核实签发状态时，才可用受限管理密钥文件申请新包。若密钥已更换或自动登录失败，让用户自行登录管理页处理，不索要密钥。

邀请 POST 发出后，超时、响应丢失或本地保存失败都可能意味着服务器已经签发。脚本会保留 `.bot-binding-pending`（`0600`、无邀请秘密）并阻止自动再次签发。管理员先在管理页检查 Bot 组、邀请和已有设备：若能从已有可信私有副本取得已签发的原包，将其原样私有保存到原 `bot-binding.json` 后走复用，无需新签；不要假定管理页能重新导出原邀请。若不能取得原包，必须先查清并撤销结果不明的邀请，再确认是否需要新签；撤销邀请不等于撤销已有设备。

只有已有 pending、没有已保存包，且管理员已完成查组/撤销后，才可显式运行：

```sh
bash /opt/salcara-hub-bot/create-bot-binding.sh \
  --install-dir /opt/salcara-hub-bot \
  --confirm-prior-invite-revoked
```

该选项是操作者确认，不是脚本自动证明撤销；普通安装/续跑绝不自动传入。**不得直接删除 pending 标记、删除绑定文件、另建空卷或重复初始化来重试**；无法确认服务器结果时保持阻断并交由管理员处理。

## 绑定包、地址变更与恢复

- 绑定包经可信私有文件渠道交付，不 `cat` 其内容、不把邀请或签名粘贴到聊天。已有包的本地结构检查不能替代 Hub/客户端的真实验证。
- 迁移或重装前停止准确的 Hub 项目，制作完整 `DataDir`（Docker 内 `/data`）的一致性私有备份：保留 Bot 组、邀请及撤销记录、手机/电脑设备身份与凭据摘要、签名密钥和 Hub 身份，以及其余管理、消息和持久状态。只有绑定包或一个 seed 不能恢复原组、设备和信任关系；手机/电脑本机绑定凭据及 pin 也须保留，不能从服务器摘要还原客户端秘密。Compose/env、反代/TLS 等卷外配置另行备份。
- 恢复先写入新的受限目录/副本卷，验证后再切换；不得让旧卷和克隆卷同时作为同一站点服务，不重新 `-init`，也不把一份旧数据备份当作已恢复当前撤销状态。完整步骤见 [Bot 数据与身份恢复](STANDALONE-DOCKER.zh.md#bot-数据与身份恢复)。
- canonical Hub URL 变化时，旧 v1 绑定 JSON 的地址受签名约束，不得手改 `hubUrl`、邀请或签名。尚未绑定的新设备需要管理员按当前 canonical 地址签发新的首次邀请包；部署脚本调用的创建邀请端点会新建组。管理员也可在原组通过 `phone/reset` 显式确认、核对版本并幂等重置手机后重新签发，但这会撤销旧手机凭据并更换邀请，不是无影响的地址刷新。已绑定设备正常迁址只走同身份恢复，不调用 reset 或再次 bind；安装/续跑脚本不会自动重置手机。旧包不能靠改文字变成新包。
- 已绑定设备恢复连接必须保留本机绑定和身份 pin，核验原公钥签名的入口清单、Hub 身份、有效期及新的 nonce 证明，并确认候选完整 URL 是签名清单中的精确成员后，才发送已有凭据；仅同公钥挑战响应不够。这是恢复已有连接，不是第二次 bind。不得把旧设备 secret 交给未验证的新站点。身份不匹配时停止，由管理员查明，不能清空 pin 或用新邀请掩盖恢复失败。
- 无稳定域名、可达的已知入口或仍有效的受信入口缓存时，保留数据也不会自动发现新 IP；需要管理员通过可信渠道提供新地址，再执行同身份校验。

## 必须验收并记录

按层记录证据；安装/续跑成功不等于下面全部通过：

| 层级 | 检查内容 | 能说明什么 / 不能说明什么 |
| --- | --- | --- |
| 本地运行 | 核对 Hub 产品、目标版本 `0.5.4` 和 `/healthz` | 仅当前容器健康，不能证明公网或设备连接 |
| 未认证公开路由 | HTTPS `/v1/ping`；无凭据虚拟设备请求返回 `400/403` | 仅基础入口响应符合预期，不能证明认证、持续收流、长轮询等待或无缓冲 |
| 部署检查记录 | 私有 `bot-deployment-checks.json` | 仅记录上述有限范围，不是端到端（E2E）验收凭证 |
| 管理与页面 | 用户登录/更换密码；另行核对页面、安全头和原服务 | 未实际操作的项目列待验收，不能从 ping 推定成功 |
| 已认证传输 | 用户自己的电脑、手机手动检查持续连接、事件到达、重连与代理缓冲 | 安装器未测试，需独立设备端证据 |
| 任务往返与原生宿主 | 实际请求、进度、结果和原会话连续性 | 本次不调用真实 Agent/付费模型，保持待验收；需要时另获授权、由用户在受控会话手动验收 |

检查记录必须如实保留：`scope="unauthenticated-public-route-only"`；`authenticatedSSE`、`authenticatedLongPoll`、`proxyBuffering`、`taskRoundTrip` 均为 `"not_tested"`；`readyForTasks=false`。不能把绑定包签发成功、预期拒绝码或脚本退出成功改写为这些项目通过。设备端验收另行留证，不手工把脚本记录改成 E2E 凭证。

- 运行的是已独立确认的正式 Bot 镜像，或记录了源码提交和本地镜像 ID 的源码构建镜像；目标 Hub 版本 `0.5.4`，非 root、只读、仅回环发布端口，无 Docker socket。源码及文档变更不代表已发布。
- 本地 health 正常；公网说明和管理页可达、query 303 清除、同源 iframe 安全头正确、未登录管理 API 返回 401，均需单独实际检查，不由安装器的路由检查代替。
- 原 Sub2API 页面和只读健康未受影响；不发送付费模型请求当健康检查。
- 管理页管理密钥登录/更换管理密钥由用户自行输入秘密验收；不要将管理密钥读取到工具输出或要求用户发管理密钥。未做这一步就列为待用户验收。
- 由用户在自己的测试设备上通过可信渠道导入绑定包，检查组内电脑、设备状态和重连；不把设备 secret、邀请或会话正文收进报告。未测的手机绑定、SSE/长轮询、代理缓冲和原生桌面续聊分别列为待验收，不保证官方宿主未开放的能力。
- 写一份无秘密的部署 MD：镜像/digest、卷名、准确变更/备份位置、只读验证结果、恢复步骤和未验收项。文件留在用户私有工作区，不能上传真实服务器配置。

## 交付给用户的格式

使用部署时的实际 URL 替换以下占位符，所有结果必须来自真实验证：

```text
Hub 容器本地健康：已检查（或说明未完成项）
公开 HTTPS 基础路由：已检查（仅未认证 ping / 虚拟设备 400 或 403，或说明未完成项）
管理后台：https://relay.example.com/salcara-hub/admin/
自定义 iframe「远程管理」URL：https://relay.example.com/salcara-hub/admin/（管理员可见）
自定义 iframe「远程使用说明」URL：https://relay.example.com/salcara-hub/（普通用户可见）
初始管理密钥文件：/opt/salcara-hub-bot/secrets/admin-initial-login.txt（由用户自己安全读取，勿公开）
文件里只有管理密钥一行，直接复制整行到管理页；首次登录后更换管理密钥，再删除本地初始文件副本。
Bot 绑定文件：/opt/salcara-hub-bot/bot-binding.json（只交付路径，用户通过可信文件渠道导入，不展示内容）。
检查记录：/opt/salcara-hub-bot/bot-deployment-checks.json（非 E2E 凭证，readyForTasks=false）。
待验收：用户登录/更换管理密钥、真实设备绑定、已认证 SSE/长轮询、代理无缓冲、真实任务往返与原生桌面续聊（按独立证据填写）。
```

不提供含管理密钥、token、用户名 query 的 URL。管理员菜单可见性不是登录授权；普通用户配对不需要审批。若用户曾把服务器登录密码发在聊天，部署后提醒用户更换，但不擅自更改 SSH、服务器登录密码或访问策略。

交付时附上 [更新与资源](STANDALONE-DOCKER.zh.md#更新与资源)、[停止或卸载](STANDALONE-DOCKER.zh.md#停止或卸载) 的指南。任何升级/卸载均先备份、只操作准确的 Hub 项目，不删除数据卷，不把原 Sub2API 当作 Hub 的附属服务停止。

遗失管理密钥时按 [服务器恢复](STANDALONE-DOCKER.zh.md#管理密钥遗失或需要恢复) 处理：先停止 Hub 并备份，复用同一个数据卷运行 `-reset-admin-key`，新随机密钥只在 `0600` 文件中，不读取到工具输出，不发聊天。重启、保护导出副本并告知用户自行读取即可；绑定/封禁数据保留，不运行首次安装初始化。
