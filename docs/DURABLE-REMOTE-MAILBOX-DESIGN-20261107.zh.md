# 远程消息持久存储与自动清理设计

状态：2026-11-07 已进入本地实现与测试阶段，尚未部署。Hub 的 SQLite 加密存储、固定期限执行票据、持久事件及确认、图片分片与引用清理、缩略图、默认关闭的离线队列和管理设置已落入代码。实际接口、验证记录与边界见 [本地实施说明](DURABLE-REMOTE-MAILBOX-IMPLEMENTATION-20261107.zh.md)。下文保留提出设计时的源码基线与验收要求，不能把所有设计目标视为已完成线上验收。

## 1. 设计提出时的源码基线与缺口（历史记录）

| 位置 | 当前实现 | 缺口 |
| --- | --- | --- |
| Hub 数据卷 | `compose.yml` 的 `hub-data:/data`，配置 `SALCARA_HUB_DATA_DIR=/data`；现有单写实例锁 | 已有持久目录，可在其内增加存储，不需要额外建一台服务器 |
| Hub 回执 | `internal/hub/command_receipts.go`：只保存 owner/hash/到期时间，24 小时；总 4096、单 owner 256 条 | 完整结果只在内存；重启只能恢复“不确定”，不能还原结果 |
| Hub 事件 | `config.go` / `store.go`：内存 ring；默认账号 2000、会话 500 条，受资源预设限制 | `event_sequence.go` 仅保存序号高水位，事件和批次去重内容重启后丢失 |
| Hub 推送 | `push.go`：token 持久化，待推送任务在内存 | 推送进程重启后需要可恢复的通知任务；取回正文不能依赖推送成功 |
| Bridge 上传 | `internal/hubclient/client.go`：内存队列默认 5000 条 / 8 MiB | 断网可排队，进程重启会丢；需要磁盘发送箱 |
| Bridge 附件 | `attachments.go` / `attachment_budget.go`：临时目录、24 小时；分片内存 1 小时，256 MiB / 1024 文件，分钟清理 | 关键未结操作引用的附件需要受管持久目录和引用保护 |
| 手机 | 本地草稿、图片副本、待确认记录已有持久化；当前安全重试窗口 23 小时 | 新服务器保存期不能直接当作旧手机的重试期；需能力协商 |

现有电脑输入 sidecar 主要保存技能/引用等显示元数据，不是覆盖所有 start/send/continue 的执行去重账本。电脑完整会话仍由原 Agent 历史管理。Hub 当前电脑离线时返回 `computer_offline`，没有服务器待执行信箱。

## 2. 三端职责与交付顺序

建议采用：**手机本地发送记录 + Hub 持久收发箱 + Bridge 执行账本**。

```text
手机保存原文、附件来源和操作编号
  → Hub 完成持久事务，回复“服务器已保存”
  → Bridge 落盘认领并校验来源，回复“电脑已接收”
  → 电脑执行，落盘结果和待上传事件
  → Hub 落盘结果，确认该事件批次
  → 手机拉取并写入本地，再确认“已同步到手机”
```

“服务器已保存”“电脑已接收”“已同步到手机”分别代表不同完成点。TCP 收到数据、HTTP 请求到达、画面已经渲染，都不能代替落盘确认。

第一期先做回执、结果和事件恢复，不改变当前电脑离线时的执行规则。第二期再提供可选“电脑上线后执行”，仅开放允许延迟的新建/发送操作，默认执行有效期 **10 分钟**。过期只保留原文供处理，不能隔几天自动执行旧指令。审批、停止、Git 写操作、依赖当前轮次的 steer/continue 不进入通用离线队列。

纯 Direct 没有 Hub 参与，应使用电脑本地持久账本与发送箱。若要使用服务器副本，需要明确选择并启用该 Hub 的恢复存储；不能自动向另一个服务器复制直连内容。

## 3. 推荐存储结构

在当前单写 Hub 中新增 SQLite（新依赖）并使用 WAL；内存 ring 保留为热点缓存。确认前完成事务提交，可靠接收路径使用能保证提交落盘的配置，例如 `synchronous=FULL`。数据库、WAL 和附件均放在同一个受管持久卷，不能将 SQLite 文件放进多个 Hub 共写的网络盘。多实例模式另行采用共享事务数据库与对象存储，本期不引入。

建议目录：

```text
/data/remote-store/messages.db
/data/remote-store/blobs/<随机对象编号>
/data/remote-store/staging/<上传编号>
```

建议逻辑表：

- `operations`：绑定/凭据世代、电脑、Agent、项目、来源身份、操作编号、正文摘要、状态、执行截止时间、结果版本、内容保留期限。
- `events` / `message_snapshots`：会话、单调序号、稳定事件编号、完整或累计正文、终态；按会话与序号分页恢复。
- `event_batches`：Bridge 批次编号、摘要和返回水位；与事件同事务写入，重复批次返回同一确认。
- `phone_cursors`：该手机在该绑定世代下已完成本地持久化的连续水位；存在缺口不能跳过确认。
- `blobs` / `blob_refs`：大小、校验值、上传状态、引用者、租约、过期时间；大文件不放进 SQLite 行。
- `push_jobs`：操作编号、通知类别、到期时间和尝试次数；无任务正文，按任务合并通知。

Bridge 同步增加持久 `operation ledger` 和 `event outbox`。原批次编号、操作编号和摘要必须跨重启保留；只有收到 Hub 持久确认后，才移除待上传记录。流式输出按短批次（建议 100–250ms / 64KiB）提交，并合并已被完整累计快照覆盖的中间片段；最终消息、任务终态和执行回执优先提交。明确的确认仍须等对应批次落盘，不能先确认再异步刷盘。

只保存恢复必需的发送内容、结果和附件。任意文件读取结果、终端/浏览器实时画面、API 密钥、配对 token、短期来源授权不纳入通用持久回执。正文和附件设计为加密存储，密钥持久保管并有轮换版本；账号/绑定隔离和访问鉴权始终保留。磁盘加密不等于端到端加密。管理员页面显示容量和状态，不展示用户正文。

## 4. 清理默认值

以下是拟定默认值，按站点配置并可对单个绑定收紧；保存期限与执行有效期独立。

| 数据 | 建议默认保留 | 清理条件 |
| --- | --- | --- |
| 未完成上传分片 | 无进展 1 小时 | 上传租约失效且未被已接受操作引用；更新活动时间不能无限延长总配额 |
| 手机未确认收取的正文、最终回复 | 7 天，可配置 1–30 天 | 按终态时间计；超期返回“恢复副本已过期”，可转向电脑历史补读 |
| 手机已落盘确认的正文、结果 | 确认后 24 小时 | 不再被未结操作或其他保留记录引用 |
| 连续流式中间片段 | 最长 24 小时 | 已有更完整累计快照覆盖；终态/最新快照按结果保留期处理 |
| 附件 | 跟随引用者；无引用后再留 24 小时 | 未结操作、保留消息、活动上传/下载租约均不再引用 |
| 尚未执行的可选离线任务 | 执行有效期 10 分钟，正文留 7 天 | 到执行截止时间转 `expired`，停止下发；不能把正文保留 7 天理解为可自动执行 7 天 |
| 已完成/取消/过期的防重摘要 | v2 默认至少 30 天 | 已超过所有服务端票据的执行期限及恢复余量，才可清理 |
| 已派发但结果不明 | 首次进入 `uncertain` 起正文最多 7 天，状态独立保留 | 重复查询不刷新该期限；始终是 `uncertain`，不能由清理器改为“未执行”或重新入队 |
| 推送任务 | 最长 1 小时重试 | 过期合并/丢弃提醒任务，正文仍可拉取；不得因推送失败重发业务命令 |
| 运行日志 | 7 天且有字节上限 | 轮转删除，不记录正文或凭据 |

进行中的任务保留必要状态与最新累计快照，受单任务/绑定配额约束；不能为保留无限中间输出占满磁盘。清理仅覆盖本功能创建、清单登记的文件，电脑项目文件、Agent 原始历史、用户另存成果不在范围内。

## 5. 清理不能破坏防重复执行

**正文到期，不代表原指令从未执行。** 不能同时删除正文和操作编号，然后把旧编号重新当作新任务。

当前 v1 请求 UUID 本身没有服务端可信的创建时间。建议 v1 未确认摘要保守保留，满额拒绝新增可靠接收；旧客户端继续原 23 小时窗口。不得声称仅把 TTL 改成 30 天就已解决长期重复执行。

v2 增加服务端签发的执行票据，绑定 `operationId + scope + payloadHash + storageEpoch + dispatchNotAfter`。采用两步准入：

1. `prepare` 只登记意图和返回票据，不允许执行；手机先持久保存票据。
2. `commit` 必须携带该票据才可进入持久派发。原票据重复提交只查同一操作，不能换新编号。

操作身份由服务端签发，包含可验证的存储世代和固定截止时间；手机原本的本地意图编号仅作首次登记关联。`prepare` 不能给已有操作续签、延长截止时间或替换票据。即使摘要已清理，服务端仍须从签名身份识别其过期状态，对旧身份再次 `prepare` 返回 `expired/unknown_expired`。要再执行须由用户明确创建新操作；自动恢复路径不得把旧意图当作无身份的新提交。这条约束由服务端强制，不能只依赖手机不重试。

这样，原回执与摘要被合法清理后，过期票据仍永远不能执行。查询无正文时返回 `expired/unknown_expired`，不能返回可重新执行的“未找到”。票据过期只限制再次派发，不强制终止已开始的电脑任务。签名密钥轮换、绑定变化和存储世代变化都要有明确的验证与失效规则；不能把失败旧票据自动转换成新任务。

Bridge 执行前记录 `claimed/executing`。执行已可能发生但尚未写入结果时崩溃，重启保持 `uncertain`，按原编号/Agent 历史核对。查不到消息不是未执行证明。通用命令无法仅靠 SSD 保证外部动作“恰好一次”，因此不得自动重放该窗口中的操作。

## 6. 图片专用清理与内存控制

图片同时占磁盘和运行内存，需要两套独立预算。一张 4000×3000 的图片，RGBA 解码约占 46MiB；压缩文件即使只有几 MiB，也不能按文件大小估算显示内存，GPU/画布副本还可能增加占用。服务器磁盘留存不能解决手机同时解码大量原图的问题。

### 图片生命周期与可删除条件

每张原图记录所属绑定、内容摘要、字节数、尺寸、引用关系、访问/上传租约和删除状态。引用至少包括草稿、待派发操作、执行中操作、结果不明操作、保留中的结果、尚未保存的画布编辑。原图不可变；批注和导出产生独立版本，恢复旧版本不能覆盖原文件。

| 图片类别 | 建议清理策略 | 保护条件 |
| --- | --- | --- |
| 上传一半的 `.part` / 分片 | 无进展 1 小时清理；上传预留配额，租约续期受总时长/大小限制 | 活跃合法上传不能被中途删除；完成后校验摘要再原子发布 |
| 待发、执行中、结果待确认的原图 | 普通缓存清理和 LRU 都不能删除 | 在其操作内容保留窗口内锁定引用；内容到期须先事务化归档/过期引用，保留缺图/已过期及防重状态，禁止再下发缺图命令 |
| 已被手机持久确认的原图 | 对应消息保留期结束且无其他引用后，再留 24 小时 | 多条消息、版本或设备引用同一图时，全部解除后才可删除 |
| 缩略图/屏幕预览图 | 可重建缓存；建议 7 天 TTL，并按最近使用时间和字节预算提前淘汰 | 不影响原图、草稿及发送状态；原图过期后不能承诺仍可重新生成 |
| 用户明确另存的成果 | 不由恢复缓存清理器删除 | 文件所有权归用户，不因引用缓存到期删除用户文件 |

同一绑定内可按内容摘要去重，只存一份相同原图；缩略图键包含原图摘要、目标尺寸和渲染版本。跨绑定默认不共享对象或公开内容摘要查询，避免一方清理影响另一方。图片只在服务端成功接收完整文件并建立合法引用后才允许用于下发。

### 手机图片内存

- 会话列表只取缩略图；建议长边 512px、压缩目标不超过约 100KiB。长图按适配比例生成小预览，查看细节时再请求分块或较大预览。
- 点击打开先取最长 1600–2048px、最多 4MP 的屏幕预览，用户需要原始细节时再按需读取原图；不自动把所有历史原图解码。
- 仅加载可视区域和一屏预取；原图查看以当前一张为主，离屏取消未完成请求、解除订阅并释放解码/GPU/画布引用。关闭预览、切会话、后台和系统内存压力事件清可重建内存缓存，保留磁盘草稿/原图引用。
- 建议图片解码工作集软目标 32MiB，低内存设备 16MiB；由像素预算约束解码尺寸，不能把这当整个进程 RSS 的硬保证。大图优先屏幕尺寸采样，放大使用分块，不默认一次解码全部原图。
- 图片下载沿用现有最多 2 个并发；同时预处理/解码建议 1 个。多个组件读取同一来源图共享在途请求与引用计数，最后一个使用者离开才可取消/回收。
- 组件状态只存文件 URI、尺寸和摘要。传输分片的 Base64 用完释放，不在消息列表、撤销栈和版本列表中保留完整 Base64/像素副本；批注撤销保存矢量操作，导出按需生成一份新图。
- 手机可重建图片磁盘缓存建议 64MiB / 7 天 LRU，单独于草稿/待确认附件持久目录。清缓存不会清草稿原图；缺图状态必须可见并阻止静默只发文字。

### 服务器/电脑的图片内存与空间

- 原图上传继续兼容当前每图最大 **8MiB**、每次输入最多 **4 张**；新增持久分片逐块写文件并增量计算摘要，单缓冲建议约 256KiB、并发 2，避免把多个完整 Base64 图长期存在内存。服务器存储只转交原文件时不解码图像。
- 缩略图异步生成，默认单 worker，并设独立工作内存上限（建议 96MiB）。解码前从真实文件头核验尺寸和总像素，不能信任手机传来的 width/height；普通处理建议不超过 16MP，预览结果不超过 4MP。支持采样的格式按目标尺寸解码；无法在预算内处理的图片保留文件但不自动生成预览，明确告知预览限制，不改写原图。
- 缩略图缓存建议全站不超过 `min(128MiB, 总预算的5%)`、每绑定 32MiB，并计入总容量。它先于有引用原图被淘汰；不能把缩略图/暂存目录当成总预算之外的无限空间。
- 原图、分片、缩略图、导出临时图均计入配额。预留目录使用量、上传中已预留字节和待删除但未成功释放的字节都计数，避免并发上传超卖空间。
- 图片清理使用引用表和受管清单：先标记待删、禁止新引用；活动读取租约结束后删除；成功后才释放占用计数。清理与上传/下载/导出同时发生时，不能让一个来源删除另一个来源的新文件。
- 容量紧张时，先清无引用分片和可重建缩略图，再清已确认且保留期结束的原图；仍不足就拒绝新上传并保留手机附件，不能删掉待确认原图腾空间。已过期图显示“图片恢复副本已过期”，不得显示成仍可发送的完好附件。

图片专项验收包含：连续滚动数百图后的内存趋稳、后台后解码缓存释放、同图多引用只清最后一份、未确认/画布编辑图不被误删、上传中断可清理且不派发缺图任务、清理与下载并发、清理进程被杀后续清、缩略图可重新生成、超大像素但小文件不撑爆内存、空间不足时手机草稿仍可恢复。上述预算为实施起点，需真实 Android/iOS 设备与当前 384MiB Hub 容器实测调整。

## 7. 定时清理、配额和故障恢复

- 复用现有 janitor，启动恢复未完成清理后，每 **5 分钟**按过期索引取小批次（建议最多 500 条或 50MiB），限制单轮耗时，避免整盘扫描阻塞消息。
- 清理分阶段：事务内复核状态/引用/租约并标记 → 移除受管文件 → 记录完成。标记后阻止新引用，崩溃后继续同一批，不因重复清理报错或删掉新文件。
- 执行截止时间在每次派发事务中检查，到期即不可派发；清理器晚跑不能延长执行资格。
- 初始建议全站预算 `min(5GiB, 卷容量的10%)`、每绑定 256MiB，并沿用现有单附件/请求限制。数据库、WAL、暂存、缩略图、正文及相关日志占用一并核算；配置值需要落在本机可用空间内，重启和运行时均重新检查可用空间。
- 70% 水位提示管理员，85% 优先回收已确认且无引用的缓存；达到预算或系统剩余空间不足 `max(2GiB, 卷容量的5%)` 时拒绝新增大正文/附件。为已有操作的结果、状态和防重摘要预留预算，保证新接收前完成容量预留。
- 预留的是有上限的状态/终态/去重记录和正文预算，不能承诺保存任意大的 Agent 输出。建议每操作累计正文/快照上限 2MiB，附件另计；超限保留终态、已有有界快照、`truncated` 和电脑补读位置，不能显示为“完整结果已保存”。元数据预留与大对象预算分开，不为接纳新任务淘汰未结状态。
- 磁盘满、只读或提交失败：不能回答“服务器已可靠保存”，也不能继续派发未保存的命令。已有内容保留；手机保留本地待发/待确认记录。
- 访问时仍检查 TTL，即使定时任务没跑也不返回过期正文。数据库使用受控 checkpoint/增量空间回收；逻辑过期、文件删除和卷占用下降不是同一个瞬间。
- 普通重启沿用原存储世代并恢复队列；明确恢复旧备份时，恢复流程必须产生新世代，触发手机 `resetRequired → 快照 → 逐页补齐`。不能声称系统能够自动识别所有外部磁盘回滚。
- 解除绑定立即停止该来源访问和派发，正文进入清理流程；紧凑防重记录隔离保留，新的绑定不能取得旧内容或重新执行旧操作。

管理页建议仅提供：恢复存储开关、正文保留天数、容量上限、离线任务是否启用及执行有效期、当前占用、待确认数量、最早恢复时间、最近清理结果。手动清理默认只处理已确认缓存；涉及未结数据时展示影响。清理不得解除未知执行状态。

## 8. 实施次序与验收

1. 完整结果持久化、Bridge 通用操作账本、v2 准入票据和能力协商；旧 hash-only 记录只迁移为 `uncertain`，不伪造结果。
2. Hub 持久事件/批次与 Bridge 磁盘发送箱；手机先落盘后 ACK，后台/冷启动按原水位恢复。
3. 附件引用、持久分片、配额、定时清理和管理页；现有临时文件只在校验完整且有合法所有者时迁移。
4. 可选离线下发，按动作白名单与执行截止时间启用；换 API/Agent/项目、过期审批不能沿用旧队列执行。

必须验证：接收前后掉电、认领/执行/写结果前后崩溃、重复事件批次、手机本地 ACK 前崩溃、断网 7 天跨 TTL、正文清掉后重放旧票据、清理与下载并发、磁盘满/只读、存储回滚、换绑定、缺附件、电脑下线后手机仍可取已存结果，以及正常 Direct 不向未选择 Hub 上传内容。

以上均为后续实现与故障注入验收项，本设计文档不代表已经上线服务器缓存或自动清理功能。
